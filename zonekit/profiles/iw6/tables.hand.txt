# chain_14029cc20 - one 0x78 record of that array.  Only two things in it touch the file:
#   +0      FUN_14029c7e0(0), a whole scriptable asset streamed here
#   +8      a buffer whose LENGTH IS A BYTE INSIDE THAT SCRIPTABLE - see the UNSUPPORTED below
# Everything after `mov ecx,2; call 1402b8330` at 14029ccb1 is inside a runtime block (rule 5) and
# reads nothing, even though two of those blocks contain a flag 1 FUN_1402b8430:
#   +0x28   flag 0 four byte name fixup (outside the block, but flag 0, so nothing)
#   +0x38   FUN_1402a49e0(0), an xmodel slot, inside push(2)          - no file bytes
#   +0x40   (u8 at scriptable+0x35) << 2, inside push(2)              - no file bytes
#   +0x48   (u8 at scriptable+0x39), inside push(2)                   - no file bytes
# then four more empty push(2)/pop pairs.  Verified instruction by instruction, not inferred.
#
# The +8 count: `movzx r8d, byte ptr [rcx+0x3a]` where `rcx = *(record+0)`, i.e. it DEREFERENCES
# the scriptable asset pointer at +0 and reads a byte at 0x3a of THAT struct.  `u8@off` is this
# struct and `u8@^off` is the enclosing asset (col_map_sp here, not the scriptable), so neither
# reaches it - but MARK plus `u8[<expr>]` does.  The scriptable that `AT|0|f14029c7e0` streams
# begins at exactly the file position that was current when the AT ran, so MARK taken immediately
# before it IS that struct's base and `u8[$cc20scriptable + 0x3a]` is the byte the reader loads.
# `.` + 0x78 would NOT work in its place: these records come from a LIST, so all the 0x78 structs
# are read first and record k's tail does not start at its own base + 0x78.
#
# That only holds when the scriptable is really streamed here.  A slot holding a back reference
# (high dword 0xfdfdfdf3) streams nothing and the mark then points at unrelated bytes, so that
# case stays UNSUPPORTED - and only when +8 is actually non null (a sum of the two halves of the
# qword: `|` is the table's field separator and cannot appear inside an expression, and the
# evaluator uses Python integers, which do not wrap, so the sum is zero exactly when the qword
# is null).
#
# The back reference case is real and it is NOT resolvable here, which was checked rather than
# assumed.  Instrumenting the walk over the whole install: almost every record of this array has a
# null +8 and does nothing at all; exactly two records per affected zone have a non null +8, the
# first with an inline scriptable at +0 (the BYTES branch, which works), the second with a back
# reference - mp_dart holds 0xfdfdfdf3084d5e65 there and mp_frag 0xfdfdfdf308d7b4a5.  Those low 32
# bits are not a file position: the sixteen scriptables that mp_dart actually streams inline sit at
# 0x0efedd56 through 0x0f301ae6, nowhere near 0x084d5e65.  The loader resolves such a value with
# `func_0x00014017fbb0(*p,&idx,&off)` into `blockbase[idx] + off`, i.e. an address inside an
# already allocated stream block, and this walker tracks file offsets only and has no block bases.
# So the byte at scriptable+0x3a is genuinely not reachable from a file position, and 10 zones stop
# here.  Do not guess the size: a wrong one desynchronises everything after it.
### f14029cc20   chain_14029cc20
SELF|0x78
MARK|cc20scriptable
AT|0|f14029c7e0
IF|u32@4 == 0xfdfdfdff
BYTES|8|u8[$cc20scriptable + 0x3a]
ELSE
IF|u32@8 + u32@0xc != 0
BYTES|8|u8[asset@0 + 0x3a]
ENDIF
ENDIF

# FUN_1402934f0 - the fx asset head: a name, then the element-definition array.
# The array count in the code is a THREE term sum
#   *(int*)(base+0x1c) + (int)base[3]/*0x18*/ + *(int*)(base+0x14)
# which the one operator count language cannot hold. Split into three consecutive LISTs on the
# SAME pointer slot 0x38: the records are contiguous and each LIST resumes where the previous one
# stopped, so the bytes consumed and the per record order are byte identical to one summed LIST.
### f1402934f0   FUN_1402934f0
SELF|0x40

#  - "runtime block" = func_0x0001402b8330(2) .. FUN_1402b82b0(): transcribed as

#
# The chain, and every call site of it is unique (a byte scan of .text for E8/E9 finds exactly one
# caller for each, so the nesting below is the only nesting there is):
#
#   type03 xmodelsurfs  0x1402a4c00   asset struct 0x38, array at +8 of u16@0x10 records

# push, so there is no `_e1` table - the loop body IS this table. Eleven calls to FUN_1402b8430:
# one for the whole array up front (imul r8, rdx, 0xe8 with the caller's own flag -> SELF 0xe8 and

#

# and the size registers are loaded from BOTH:
#
